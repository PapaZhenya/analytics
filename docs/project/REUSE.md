# Callytics → Local QA Platform: что оставить, что заменить, что удалить

Контекст: текущая ветка называется `feature/local-qa-platform` — это явный сигнал, что цель
проекта смещается от "call-analytics демо" к **локальной QA-платформе** (проверка качества
диалогов/звонков). Ниже — оценка каждой части кодовой базы именно под эту цель, основанная
только на фактически прочитанном коде (см. `PROJECT_ARCHITECTURE.md`, `PIPELINE.md`,
`MODULES.md`). Это анализ — никакие изменения в коде не выполнялись.

## 1. Уже идеально подходит — оставить как есть

Эти части имеют чистую однозадачность (single responsibility), не зависят от специфики
"контакт-центра" и переносимы в QA-платформу без переделки:

- **`SilenceStats` (`src/audio/metrics.py`)** — чистый, самодостаточный статистический класс
  без внешних побочных эффектов. Считает тишину между репликами — ключевая метрика для любой
  QA-платформы (не только контакт-центра): долгие паузы = сигнал проблемы разговора.
- **`Audio.properties()` (`src/audio/analysis.py`)** — извлечение акустических признаков
  (RMS, EQ, ZCR, spectral centroid, MFCC) не завязано на домен "звонок в поддержку"; полезно
  для любой аудио-QA (оценка технического качества записи).
- **`SpeakerTimestampReader` / `TranscriptWriter` (`src/audio/io.py`)** — простые,
  предсказуемые парсер/экспортёр, без доменной специфики.
- **`WordSpeakerMapper` / `SentenceSpeakerMapper` (`src/audio/analysis.py`)** — универсальный
  механизм сборки "кто что сказал и когда" из независимых сигналов (ASR + диаризация); не
  привязан к бинарной модели Customer/CSR на уровне алгоритма (ограничение появляется позже,
  на уровне LLM-промптов и схемы БД — см. ниже).
- **Пайплайн-стадии как отдельные классы** (`DialogueDetecting`, `SpeechEnhancement`,
  `DemucsVocalSeparator`, `Transcriber`, `ForcedAligner`) — хорошее разделение ответственности
  по стадиям, каждая стадия — заменяемый "кубик". Сама архитектура "конвейер независимых
  стадий" хорошо подходит под QA-платформу.
- **`ModelRegistry` / `ModelFactory` (`src/text/model.py`)** — расширяемый паттерн для
  подключения новых LLM-провайдеров без изменения вызывающего кода — хорошая основа, если
  QA-платформе понадобится гибкий выбор модели (например, локальная модель для приватности
  данных вместо OpenAI).
- **Реляционная схема `Topic`/`File`/`Utterance` (`src/db/sql/Schema.sql`)** как отправная
  точка — простая, понятная, легко расширяемая (см. "заменить" ниже про ограничение по ролям).

## 2. Оставить, но доработать

- **`SentenceSpeakerMapper`/`WordSpeakerMapper`** — оставить механизм, но убрать неявную
  привязку downstream-кода к ровно двум ролям (см. ниже про промпты и схему БД) — сам
  маппинг уже поддерживает произвольное число спикеров, ограничение появляется только позже
  в пайплайне.
- **`Cleaner` (`src/utils/utils.py`)** — сам класс (удаление временных файлов) полезен и
  универсален, но его **текущее использование на Шаге 18 недопустимо для QA-платформы**:
  `cleaner.cleanup(temp_dir, audio_file_path)` удаляет исходную запись звонка целиком.
  QA-платформе почти всегда нужно **прослушивание оригинала** для ручной проверки решений
  модели (человек должен уметь верифицировать, почему ИИ поставил такую оценку). Использовать
  `Cleaner` только для `.temp/`, но не для исходного аудио — это архитектурное решение,
  которое нужно менять на уровне вызова в `main.py`, а не на уровне самого класса.
- **`DialogueDetecting(delete_original=True)`** — тот же риск удаления оригинала, только на
  Шаге 1 (если диалог не распознан). Для QA-платформы предпочтительнее сохранять файл (или
  перемещать в "не распознано" директорию) вместо удаления — теряется возможность
  расследовать, почему детектор не увидел диалог.
- **`Watcher` (`src/utils/utils.py`)** — концепция "следить за папкой и обрабатывать новые
  файлы" разумна для локальной платформы, но текущая реализация: 1) блокирующий
  `while True: time.sleep(1)`, 2) `asyncio.run(callback(...))` внутри синхронного колбэка
  `on_created` — обрабатывает файлы строго по одному, без очереди и без устойчивости к сбоям
  (если `main()` упадёт на середине — файл не переобработается, нет retry). Для QA-платформы,
  где важно гарантированно обработать каждую запись, стоит доработать до модели с
  персистентной очередью (даже простой — например, таблица `PendingFiles` в той же SQLite) и
  явной обработкой ошибок с повторными попытками.
- **`LLMOrchestrator.generate()`** — механизм извлечения JSON регуляркой (`extract_json`)
  работает, но хрупок. Для QA-платформы, где результат LLM влияет на оценки качества,
  стоит перейти на structured output (JSON mode/response_format), который уже частично
  поддержан в `OpenAIModel.generate(return_as_json=...)`, но не используется вызывающим кодом.

## 3. Заменить

- **Промпты и ролевая модель "Customer / CSR" (`config/prompt.yaml`, `LLMResultHandler`,
  `Schema.sql: CHECK (Speaker IN ('Customer','CSR'))`).** Это самое узкое место для перехода к
  общей QA-платформе: весь стек — от системного промпта Classification до ограничения в БД —
  жёстко предполагает ровно двух участников с фиксированными ролями "клиент"/"оператор". Если
  будущая QA-платформа должна оценивать произвольные разговоры (не только обращения в
  поддержку) или разговоры с 3+ участниками (диаризация технически это уже умеет —
  `max_num_speakers: 8` в NeMo-конфиге), нужно:
  - заменить бинарную классификацию ролей на настраиваемую таксономию ролей (конфигурируемую
    per-QA-сценарий);
  - убрать `CHECK (Speaker IN ('Customer','CSR'))` в пользу более общей модели (например,
    `SpeakerRole` как отдельная таблица/enum, задаваемая на уровне конкретного QA-сценария).
- **`AzureOpenAIModel` (`src/text/model.py`)** — реализация несовместима с закреплённой версией
  SDK (`openai==1.57.0`, см. `PROJECT_ARCHITECTURE.md`, п.4.1). Если Azure OpenAI действительно
  нужен платформе — реализацию нужно переписать под новый клиент (`AzureOpenAI` из текущего
  `openai` SDK), взяв за образец уже рабочий `OpenAIModel`.
- **Способ деплоя (`automation/service/callytics.service`)** — systemd-unit с абсолютными
  путями конкретного разработчика (`/home/bunyamin/...`) и активацией conda-окружения через
  `bash -c` — воспроизводимо только на этой одной машине. Для "локальной" QA-платформы это
  ещё приемлемо (не обязательно требуется Kubernetes), но стоит хотя бы параметризовать пути
  через `.env`/переменные окружения и зафиксировать окружение через Docker (что и так в
  roadmap README как "Dockerization"), чтобы платформу можно было развернуть у другого
  пользователя/на другой машине без правки unit-файла.
- **Точка расчёта акустических метрик** — сейчас `Audio.properties()` считается по исходному
  файлу (Шаг 15), а не после Speech Enhancement/Voice Separation. Для QA-платформы, если цель
  метрик — оценка "чистоты" голоса именно оператора/участника (а не помехи линии), точку
  расчёта стоит явно выбрать (исходник vs. вокал после Demucs) — сейчас выбор скорее
  случайный, чем осознанный (объект `Audio` создаётся в начале `main()` с `audio_file_path`,
  когда ещё не существует ни enhanced, ни vocals-версии).

## 4. Удалить

> **Обновление:** оба пункта ниже выполнены при реализации Phase 1 веб-платформы — см.
> `docs/project/WEB_PLATFORM.md`, раздел "Audit fixes applied during this build".

- ~~`Denoiser` (`src/audio/preprocessing.py`)~~ — не использовался нигде в `main.py`,
  функционально дублировался `SpeechEnhancement` (MPSENet). **Удалён.**
- ~~`PromptManager` (`src/text/prompt.py`)~~ — параллельный, неиспользуемый механизм
  загрузки промптов, ссылавшийся на несуществующий файл (`config/prompts.yaml`).
  **Файл удалён** — `LLMOrchestrator` использует собственную реализацию (`_load_prompts`).
- **Неиспользуемая опция `suppress_numerals`/`TokenizerUtils`-путь**, если платформа не
  планирует её включать — либо удалить, либо осознанно прокинуть параметр из конфига в
  `main.py`, чтобы код не был "мёртвым по факту, живым по объявлению".
- **ASR-блок в `config/nemo/diar_infer_telephonic.yaml` (`diarizer.asr.*`)** — в текущем
  пайплайне транскрипция полностью выполняется через отдельный Whisper (`Transcriber`), NeMo's
  собственный ASR-модуль (`stt_en_conformer_ctc_large`) в конфиге присутствует, но нигде не
  задействован явно основным кодом (используется только диаризация из этого конфига). Если
  подтверждено, что NeMo ASR-ветка не нужна — можно убрать эту секцию конфига для ясности (сам
  диаризатор её не обязательно требует для базового `ClusterDiarizer`-режима).

## 5. Итоговая рекомендация по стратегии переноса

1. Ядро пайплайна (Enhancement → Separation → Whisper → Alignment → Diarization → Mapping)
   переносить **как есть** — это готовый, работающий "аудио-в-разметку" конвейер, доменно
   нейтральный.
2. Полностью пересмотреть точку "LLM-анализ + схема БД" — заменить бинарную Customer/CSR
   модель на конфигурируемую ролевую модель до того, как на неё будет что-то ещё
   надстраиваться, иначе миграция усложнится с ростом данных в БД.
3. Прежде чем давать платформе работать "в фоне" на реальных данных — обязательно убрать
   удаление исходных аудиозаписей (`Cleaner` на Шаге 18, `delete_original=True` на Шаге 1)
   и предусмотреть постоянное хранилище (для ручной проверки/аудита решений ИИ — это
   стандартное требование любой QA-системы).
4. Добавить тесты и CI до расширения функциональности — сейчас 0% покрытия тестами делает
   любую последующую переделку рискованной (нет защитной сетки, которая подтвердит, что
   рефакторинг не сломал пайплайн).
